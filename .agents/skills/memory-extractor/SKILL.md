# Memory Extractor — актуализатор памяти и профилировщик

## Назначение

Memory Extractor — агент автоматического обновления базы знаний проекта.

Его задача — анализировать оригинальный и переведённый/отредактированный текст новых глав, выявлять новые сущности (персонажей, термины, локации, титулы, ранги) и динамику отношений, а затем формировать выверенные предложения по дополнению файлов памяти в `memory/<project>/` с использованием **двухуровневой системы валидации статусов (`provisional` vs `confirmed`)**.

> **Каждая глава анализируется независимо.** Не читай `MEMORY_PROPOSAL.json` других глав как референс — протокол (раздел 6) уже точно определяет, что нужно прочитать (текст главы, мастер-файлы, `candidates.json`). Предложения по другим главам не содержат новой информации о текущей и только расходуют ресурсы.

---

# 1. Двухуровневая система статусов (Provisional vs Confirmed)

Для предотвращения замусоривания контекста переводчика второстепенными одноразовыми сущностями все извлекаемые записи классифицируются по статусу надёжности (`validation_status`):

### 1. `provisional` (предварительный статус)
- **Условие:** Сущность встретилась в тексте **1 раз** и не является заведомо центральной для сюжета.
- **Хранение:** Сохраняется в **буфер кандидатов** (`memory/<project>/candidates.json`).
- **Поведение в пайплайне:** **НЕ попадает** в обязательный мастер-контекст переводчика на следующие главы, чтобы не раздувать системный промпт случайными деталями.

### 2. `confirmed` (подтверждённый статус)
- **Условие:** Сущность встретилась **от 2–3 раз** в тексте, ЛИБО является **центральной для сюжета** с первого появления (имя протагониста, ключевого спутника, название столицы/родной деревни, фундаментальная система магии).
- **Хранение:** Передаётся в **мастер-память проекта** (`characters.json`, `glossary.json`, `locations.json`, `relationships.json`).
- **Поведение в пайплайне:** Входит в **обязательный контекст** переводчика и рецензентов на все последующие главы.

### 3. Механизм повышения статуса (`PROMOTE`)
При сканировании новой главы `memory-extractor` сопоставляет найденные сущности с буфером `candidates.json`:
- Если сущность из `candidates.json` встречается повторно (счётчик `occurrences_count` достигает 2–3), агент формирует директиву `PROMOTE`, переводя запись в статус `confirmed` и перемещая её из буфера кандидатов в соответствующий файл мастер-памяти.

# 2. Извлекаемые категории данных

### 1. Новые термины и топонимы (`glossary.json` / `locations.json` / `candidates.json`)
- `term_jp` / `name_jp`: оригинальный термин на японском (при наличии);
- `term_en` / `name_en`: термин в английской версии;
- `term_ru` / `name_ru`: утверждённый русский перевод / транскрипция по Поливанову;
- `category` / `type`: категория (`magic_technique`, `food`, `cultural_concept`, `flora_food`, `city`, `building`, etc.);
- `validation_status`: `"confirmed"` | `"provisional"`;
- `occurrences_count`: число упоминаний (целое число >= 1);
- `description`: краткое описание значения и контекста.

### 2. Профили персонажей (`characters.json` / `candidates.json`)
- `id`: уникальный строковый идентификатор (`character_kirishima_hayato`);
- `name_jp`, `name_en`, `name_ru`: имена на JP, EN, RU (по Поливанову);
- `gender`: `male` | `female` | `unknown`;
- `age_group`: `child` | `teenager` | `adult` | `elder` | `unknown`;
- `role`: сюжетная роль;
- `validation_status`: `"confirmed"` | `"provisional"`;
- `occurrences_count`: число упоминаний;
- `status`: `active` | `deceased` | `mentioned`;
- `speech_summary`: особенности речи и обращений.

### 3. Отношения и речевой регистр (`relationships.json`)
- `pair`: пара ID персонажей `["character_a", "character_b"]`;
- `register`: `formal` | `informal_tu` | `informal_family`;
- `validation_status`: `"confirmed"` | `"provisional"`;
- `note`: контекст перехода и правила обращения.

### Требование к содержанию `description` / `note` / `speech_summary`:
Эти поля обязаны отражать **только то, что прямо сказано или явно показано в тексте главы**: факты, реплики, действия, авторские формулировки. **Запрещено**:
- предсказывать дальнейшее развитие сюжета или отношений («это повлияет на...», «в будущем приведёт к...»);
- домысливать скрытые мотивы, чувства или намерения персонажей, не выраженные в тексте напрямую;
- формулировать интерпретации в духе литературного анализа вместо фиксации факта.

Такие записи попадают в мастер-память и становятся обязательным контекстом для переводчика и рецензентов — спекулятивное содержание «загрязняет» базу знаний недостоверными фактами, которые дальше будут восприниматься как канон.

# 3. Структурная база знаний (`memory/<project>/`)

База знаний разделена на мастер-файлы и буфер кандидатов:

### Мастер-память (только `confirmed`):
1. **`characters.json`** — подтверждённые действующие лица (имя JP, EN, RU, пол, возраст, титул, характер, статус).
2. **`glossary.json`** — подтверждённая терминология, магия, ранги, артефакты, организации.
3. **`locations.json`** — подтверждённые географические названия, города, страны, ключевые здания.
4. **`relationships.json`** — подтверждённые отношения персонажей и регистр общения («ты» / «вы»).
5. **`lore.json`** — подтверждённый лор, предыстория, важные сюжетные договоренности, правила и макро-факты мира.

### Буфер кандидатов (только `provisional`):
6. **`candidates.json`** — предварительные сущности с 1 упоминанием (`occurrences_count: 1`), ожидающие повторного появления в следующих главах.

# 4. Файлы и ресурсы

| Назначение | Путь |
| :--- | :--- |
| Исходник главы (вход) | `source/<project>/<volume>/<chapter>.txt` |
| Готовый перевод главы (вход) | `output/<project>/<volume>/<chapter>/chapter.md` |
| Предложение памяти (выход) | `qa/<project>/<volume>/<chapter>/MEMORY_PROPOSAL.json` |
| Шаблон предложения | `.agents/skills/memory-extractor/resources/proposal_template.json` |
| Пример предложения | `.agents/skills/memory-extractor/examples/proposal_example.json` |
| База знаний проекта | `memory/<project>/` |

### Скрипт применения предложений (`scripts/extract_memory.py`)
Валидирует и обновляет `candidates.json`/память проекта:
- **Атомарная запись и бэкапы:** запись через временный файл `.tmp` с `fsync` и автоматическим созданием резервной копии `.bak` перед заменой.
- **Двухуровневое сопоставление (Strict vs Fallback):** необратимые действия (`REJECT`, `DELETE`, поглощение в `MERGE`) требуют строгого совпадения по `id` или оригинальному японскому термину.
- **Безопасный Dry-Run:** в режиме симуляции скрипт не создает файлов и папок на диске.
- **Накопительный счётчик `occurrences_count`:** количество появлений сущности корректно суммируется по главам.

```bash
python3 .agents/skills/memory-extractor/scripts/extract_memory.py \
  --proposal qa/<project>/<volume>/<chapter>/MEMORY_PROPOSAL.json \
  --memory-dir memory/<project>/ \
  --apply
```

# 5. Протокол работы (Execution Workflow)

1. **Сканирование:** Прочитай оригинальный текст (`source/.../<chapter>.txt`) и готовый перевод (`output/.../chapter.md`) — по одному разу целиком, без повторных фрагментированных перечитываний одних и тех же участков.
2. **Сличение с существующей памятью и буфером:**
   - Прочитай мастер-файлы (`characters.json`, `glossary.json`, `locations.json`, `relationships.json`, `lore.json`).
   - Прочитай буфер кандидатов (`candidates.json`).
   - Ищи целевым образом — по именам персонажей, терминам и парам отношений, названным в задаче или встреченным в тексте главы. Не используй общие/несвязанные поисковые запросы (например, `"id"`, случайные слова) — они не сужают выборку и тратят ресурс впустую.
3. **Классификация найденных сущностей:**
   - Если сущность уже есть в `candidates.json` и встретилась вновь → сформируй директиву `PROMOTE` с повышением до `confirmed`.
   - Если сущность новая и встретилась 1 раз (не центральная) → статус `provisional`, добавление в буфер `candidates.json`.
   - Если сущность новая и встретилась 2+ раз ЛИБО является центральной сюжетной → статус `confirmed`, добавление в мастер-память.
4. **Формирование JSON-предложения:** Запиши `qa/<project>/<volume>/<chapter>/MEMORY_PROPOSAL.json` по структуре шаблона (раздел 4).
5. **Автоматическое применение предложений:** запусти скрипт `extract_memory.py` (команда и параметры — раздел 4).

# 6. Строгие ограничения

### Категорически запрещено:
- Добавлять сущности со статусом `provisional` в мастер-файлы (`characters.json`, `glossary.json`, `locations.json`) до подтверждения их повторного появления или ключевой роли;
- Передавать буфер кандидатов `candidates.json` в обязательный промпт переводчика;
- Игнорировать систему Поливанова для имён и японских терминов;
- Автоматически удалять сущности из буфера `candidates.json` без решения редактора проекта;
- Читать `MEMORY_PROPOSAL.json` других глав в качестве референса (см. примечание в начале документа);
- Формулировать `description`/`note`/`speech_summary` как предсказание сюжета или домысел о мотивах/чувствах персонажей, не выраженных в тексте напрямую (см. раздел 2).
